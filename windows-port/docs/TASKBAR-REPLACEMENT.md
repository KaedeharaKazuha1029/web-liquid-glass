# 替换任务栏：架构与实测结论

> v2 的核心。这一篇记录的都是**在真机上跑出来**的结论，不是推断。

---

## 一、为什么推倒重来

v1 的做法是「把玻璃垫在系统任务栏下面」——它有个绕不过去的缺陷：

**任务栏背后永远是"壁纸的最下面那一条"。** Windows 的窗口不会延伸到工作区之外，
所以无论桌面上开着什么，那 72 像素背后只可能是壁纸。壁纸一平坦，折射就没有内容可以弯折，
玻璃看上去只是"变透明"。

v2 换了个思路：**把系统任务栏整个藏起来，自己造一条。** 于是：

| | v1（underlay） | v2（replace） |
|---|---|---|
| 系统任务栏 | 保留，抹掉背景 | **完全隐藏** |
| 玻璃形态 | 通栏矩形 | **悬浮胶囊，宽度随应用数变化** |
| 图标文字 | 由 explorer 绘制 | **本程序绘制（图标在上、名字在下）** |
| 折射内容 | 壁纸最下面一条 | **整块屏幕（工作区释放后含窗口内容）** |
| 依赖 Accent API | 是（Win7 没有 → 无法适配） | **否**（Win7 也能跑） |

---

## 一′、层级：桌面之上、窗口之下（含一个把任务栏弄没的坑）

**需求**：任务栏要在**所有普通应用窗口之下**，仍在**桌面之上**，而且**看得见**。
三个目标其实两两冲突，这一节是踩完坑后的最终答案。

### 走过的弯路：寄生壁纸 `WorkerW`（v2.2.0，事故）

"桌面小组件"的常见做法是 `SetParent` 到 `Progman` 派生出的 `WorkerW`
（Wallpaper Engine 正是这么把自己当壁纸的）。我们照做了：

```csharp
SendMessageTimeout(progman, 0x052C, ...);   // 促使 Progman 派生出 WorkerW
SetParent(overlayHandle, worker);           // 寄生
```

**结果：任务栏彻底消失。** 渲染、几何、层级全部"正确" ——
实测 `overlay zIndex=433`、`Progman zIndex=434`，确实紧贴桌面 ——
但那个 `WorkerW` 是**壁纸所在层**，玻璃被画在了壁纸**底下**，用户什么都看不到，
而日志里全是"成功"。

> 教训：**`WorkerW` 是"把自己当壁纸"的层级，不是"桌面小组件"的层级。**

### 最终做法：Z 序沉底（v2.3.0 起）

保持**普通顶层窗口**，只把 Z 序压到普通窗口带的最底部：

```csharp
SetWindowPos(hwnd, HWND_BOTTOM, 0, 0, 0, 0, SWP_NOMOVE | SWP_NOSIZE | SWP_NOACTIVATE);
```

配合窗口自带的 `WS_EX_NOACTIVATE`，点击不会把它抬起来，于是它稳定停在
**桌面之上、所有普通窗口之下** —— 语义与寄生方案完全相同，但**始终可见**。
另加每 2 秒一次的自愈重设，防止 explorer 重启等事件把它挤上去。

### 补上"被窗口盖住"这半截

"窗口之下"意味着只要有窗口铺到底部，任务栏就被盖住 —— 从用户视角依然是"不见了"。
所以默认**在屏幕底部预留工作区**（`reserveWorkArea: true`，高度 = `height` + `bottomMargin`）：
本程序注册自己的 **AppBar** 把这一条从工作区里挖掉，最大化窗口于是**停在任务栏上方**。

| 目标 | 桌面层 | 不挡窗口 | 永远可见 |
|---|---|---|---|
| 寄生 WorkerW | ✅ | ✅ | ❌ 完全看不见 |
| 置顶 topMost | ❌ | ❌ | ✅ |
| **默认（Z 序沉底 + 预留工作区）** | ✅ | ✅ | ✅ |

三者能同时拿到的代价：玻璃背后是**壁纸**而非窗口内容（窗口不再延伸到底）。
`config/liquidglass.json` 里用 `zOrder`（desktopBottom / behindDesktopIcons / topMost / normal）
与 `reserveWorkArea`（true / false）自由切换。

## 二、隐藏任务栏之后，工作区不会自己回来

这是 v2 最核心的一个坑，也是投入最多实测的一处。

**现象**：`ShowWindow(Shell_TrayWnd, SW_HIDE)` 之后，任务栏窗口确实消失了，
但 `GetMonitorInfo().rcWork` 仍然是「屏幕高度 − 72」。屏幕底部留了一条死区，
最大化窗口停在玻璃上方。

**原因**：任务栏在启动时向 Shell 注册了一个 AppBar，占着屏幕底部 72px。
隐藏窗口**不会**撤销这个注册。

### 四种手段的对照实测

在 Windows 11 Build 26200 / 2560×1600 上逐个跑过：

| 手段 | 工作区结果 | 结论 |
|------|-----------|------|
| A · 只 `ShowWindow(SW_HIDE)` | `2560×1528` 不变 | ✗ 不释放 |
| B · 代任务栏提交 `ABM_SETPOS` 收缩预留 | `2560×1528` 不变 | ✗ **假成功**：API 返回非零，但工作区没动 |
| C · `SPI_SETWORKAREA` 直接改 | `2560×1528` 不变 | ✗ 被 explorer 立刻改回去 |
| **D · `ABM_SETSTATE` 开启任务栏"自动隐藏"** | **`2560×1600`** | ✅ **真正释放** |

### 最终策略：先试、再量、后升级

```
① 先试 B（把 AppBar 预留压成 1px）—— 它不改动用户任何设置
② 隐藏任务栏
③ 等 600ms，**实测 rcWork**
④ 如果没释放 → 回滚 B，改用 D（开启自动隐藏）
⑤ 再实测一次，把最终结果写进日志
```

**关键点是不能相信 API 的返回值，必须量工作区。** B 的"假成功"如果不实测就根本发现不了。

### 关于 D 的诚实说明

开启「自动隐藏任务栏」是一次**真实的设置变更**，你能在
「设置 → 个性化 → 任务栏」里看到那个开关被打开了。原因是：这是唯一一个
语义正确（"任务栏不再占用工作区"就是自动隐藏的定义）、且三代系统都支持的公开接口。

程序会：

1. 启动前记录原始状态；
2. 把它写进 `%LOCALAPPDATA%\LiquidGlass\session-state.json`；
3. 退出时精确还原（不是"设成关"，而是设回**原本的值**——用户可能本来就开着）；
4. 进程被强杀时，下一次启动会读状态文件自动修复。

## 三、崩溃安全：跨进程的状态记忆

系统级功能不能假设进程会正常退出。用户可能用任务管理器结束它、可能蓝屏。

`SessionStateGuard` 的做法是**把"改动前是什么样"落盘**：

```jsonc
// %LOCALAPPDATA%\LiquidGlass\session-state.json
{
  "originalAutoHideState": 0,          // 自动隐藏的原始位掩码
  "autoHideChanged": true,
  "originalTaskbarRect": [0, 1528, 2560, 1600],   // 任务栏原本的 AppBar 矩形
  "startedAt": "2026-09-15 19:39:12",
  "processId": 12345
}
```

- **启动时**：先读它，发现上次留下了未清理的状态 → 先把系统修回去 → 再继续。
- **正常退出**：还原 + 删除文件。
- **异常退出**：文件留着，下次启动自动修复。

还有一个容易被忽略的细节：**还原 AppBar 矩形之后，还要显式 `SetWindowPos` 把任务栏窗口拽回来**。
explorer 在预留被压小之后会把任务栏挪到贴近屏幕边缘的"隐藏位"（y 坐标超出屏幕底），
单靠 `ABM_SETPOS` 不会让它自己回来。

## 四、读取"系统任务栏的内容"

任务栏上会出现什么，规则在 Windows 内部，没有公开 API 直接列举。这里复刻了 Explorer 的判定链：

| 顺序 | 判定 | 为什么需要 |
|------|------|-----------|
| 1 | `IsWindowVisible` | 基础 |
| 2 | 非 `WS_EX_TOOLWINDOW` | 浮动面板、输入法候选框不该上任务栏 |
| 3 | 无 owner 窗口 | 有 owner 的是对话框，归到宿主窗口 |
| 4 | **非 DWM cloaked** | **最容易被漏掉的一条** |
| 5 | 标题非空，或带 `WS_EX_APPWINDOW` | 排除无意义的空窗口 |
| 6 | 不在 Shell 黑名单 | 排除 Progman / WorkerW / 任务栏自身 / 本程序 |

### 第 4 条为什么关键

**被挂起的 UWP 应用、以及位于其它虚拟桌面上的窗口，`IsWindowVisible` 依然返回 true。**
只用可见性判断的话，任务栏上会冒出一堆早已关闭的幽灵图标。
只有 `DwmGetWindowAttribute(DWMWA_CLOAKED)` 能把它们识别出来（Win8+；
Win7 没有这个属性，会退化为可能显示幽灵窗口——这一点已在文档中标明）。

### 应用身份与显示名

- **身份**：优先 `PUID_AppUserModel_ID`（通过 `SHGetPropertyStoreForWindow` 取），
  退回可执行文件全路径。前者能正确区分 UWP 应用，
  否则 Windows 计算器、照片、商店会被统统归到 `ApplicationFrameHost` 名下。
- **显示名**：取 exe 的 `FileDescription`（就是资源管理器里显示的那个名字），
  例如 `chrome.exe` → "Google Chrome"、`WindowsTerminal.exe` → "Windows Terminal Host"。
  UWP 的包名 `Microsoft.WindowsCalculator_8wekyb3d8bbwe` 会被拆成 "Windows Calculator"。

### 固定项与顺序

固定项以 `.lnk` 存在 `%APPDATA%\Microsoft\Internet Explorer\Quick Launch\User Pinned\TaskBar\`。
这个路径从 **Windows 7 一直沿用到 Windows 11**，是本移植能自动适配三代系统的另一块基石。
用户在「设置 → 任务栏」里增删固定项时，explorer 就是在改这个文件夹——监听它即可实时同步。

**顺序是 best-effort 的**：文件夹里按文件名排序，真实顺序存在注册表
`HKCU\...\Explorer\Taskband` 的二进制值里。这里把二进制按 UTF-16LE 解码后
查找各固定项文件名、用首次出现偏移排序。实测能捞到一部分（本机 5 项里命中 1 项），
捞不到的排在最后。**顺序不准只影响观感，不会导致功能异常。**

## 五、性能：为什么必须给进程路径加缓存

一次窗口扫描要过 600+ 个顶层窗口，其中 explorer 一个进程就贡献几十个。
不做缓存就是几百次 `OpenProcess`，每次都要走一遍内核对象查询。

实测：加上「PID → 进程路径」的 `[ThreadStatic]` 缓存后，整轮枚举快了一个数量级。
这是**必需**而不是优化——WinEvent 钩子要求我们对应用开关做出秒级响应。

## 六、动态同步

```
应用开关 / 窗口改名 / 前台切换
        ↓
SetWinEventHook(
    EVENT_OBJECT_CREATE .. EVENT_OBJECT_NAMECHANGE,
    WINEVENT_OUTOFCONTEXT | WINEVENT_SKIPOWNPROCESS)
        ↓
只关心 idObject == OBJID_WINDOW 的事件   ← 不筛掉子控件会把 CPU 吃满
        ↓
置脏标记（合并 180ms 内的连续事件，避免应用启动时重扫十几次）
        ↓
Tick 里重扫模型 → 重算布局 → 窗口宽度变化 → 重置累积缓冲 → 重新渲染
```

另有一条 2.5 秒的安全网重扫，兜住任何漏掉的事件。

### 实测数据

| 阶段 | 应用数 | 面板宽度（v2.0） | 面板宽度（v2.2，几何 ×2） |
|------|--------|------------------|---------------------------|
| 启动前 | 6 | 542px | 1084px |
| 新开一个记事本 | **7** | **602px**（+60px） | **1204px**（+120px，正好一个 `itemWidth`） |
| 关掉记事本 | **6** | **542px**（−60px） | **1084px**（−120px） |

**高度全程不变**（v2.0 = 58px，**v2.2 默认 = 116px**）——
这正是用户要求的"仅长度变化，不改变高度"。

## 七、踩过的最严重的坑

`TaskbarReplacementService` 最初的写法是：

```csharp
public void Dispose()
{
    if (_disposed) return;
    _disposed = true;
    Stop();          // ← Stop() 开头就 if (_disposed) return;
    ...
}
```

**`Stop()` 整个变成了死代码。** 系统任务栏没被还原、工作区没还回去、
自动隐藏开关留在了打开状态。而日志里一切正常，因为日志也写在 `Stop()` 里。

发现它的方式是**独立复核**：跑完自检后用一段独立的 Python 脚本直接读
`GetMonitorInfo` / `GetWindowRect` / `ABM_GETSTATE`，而不是相信程序自己的报告。
那一刻看到 `autohide=True` 和任务栏窗口在 `(0,1598)` —— 都在屏幕外。

修复：用独立的 `_stopped` 标志做幂等判断，不再复用 `_disposed`。
另外把「状态文件 + 独立复核」固化成了 `--verify-taskbar` 的一部分。

**这个坑的教训比修复本身更重要**：系统级功能的自检必须独立取证，不能自证。

## 八、图标与文字怎么画

### 图标

`HICON → GetIconInfo → GetDIBits → BGRA`。坑集中在 Alpha 上：

- 现代 32 位图标直接取位；
- **24 位色 + 单色掩码的老图标，其位图 Alpha 全是 0**，直接当 32 位用会整个变成透明，
  看起来就是"图标丢了"。所以要先检查 Alpha 是否真的有效，无效则回头读掩码位图反推。

缩放时**必须预乘后再插值**，否则透明边缘会出现黑边（这是图标缩放的经典错误）。

### 文字

用 GDI：在**全 0 的底**上用**纯白**画字，于是每个像素的亮度就等于字形覆盖率，
直接拿来当 Alpha。这样后续可以染成任意颜色（悬停变亮、非悬停偏灰），
抗锯齿边缘保持正确。

字体用 `Segoe UI`（Win7 起自带，中文自动回退微软雅黑），字号 10px，
配合 `DT_END_ELLIPSIS` 处理过长名字。

**为什么不用字体库**：整个仓库的承诺是零第三方依赖，而 GDI 从 Windows 2000 就在，
跨三代系统行为完全一致。

### Windows 徽标

四代系统都没有稳定的"开始图标"资源索引可提取（`shell32.dll` 的图标序号各版本不同），
所以直接画四个圆角方块——反而最稳，还能跟着主题调色。

## 九、交互

| 操作 | 行为 |
|------|------|
| 左键 | 有窗口 → 切到它；已是前台 → 最小化（任务栏经典开关手感）；无窗口 → 启动 |
| 中键 | 新开一个实例 |
| 右键 | 原生菜单：关闭窗口 / 关闭所有窗口 / 打开文件所在位置 / 任务栏设置 |
| 悬停 | 玻璃高光 + 文字变亮 |
| 点击开始 | 模拟 Win 键（系统开始按钮已随任务栏隐藏） |
| 点击时钟 | Win+N 通知中心 |
| 点击齿轮 | Win+A 快捷设置 |

**为什么不做"固定 / 取消固定"**：Windows 10 起微软移除了 `taskbarpin` / `taskbarunpin`
两个 Shell 动词，没有任何公开 API 能以"用户意图"的方式改固定列表。
自己往固定项文件夹塞 `.lnk` 在部分版本上不会被 Explorer 立刻采纳。
与其做出一个时灵时不灵的功能，不如把用户引导到唯一权威的地方——
右键菜单里的「任务栏设置」会直接打开 `ms-settings:taskbar`。
这也正好满足"Windows 设置里仍可改变除外观外的设置"。

### 命中测试（⚠️ 有一个尚未解决的坑）

**设计预期**：分层窗口的命中测试**基于 Alpha 通道**，胶囊之外的透明像素会把点击
透传给桌面，因此不需要手动做命中裁剪。

**实测打脸**：把窗口沉到 Z 序最底部（`HWND_BOTTOM`，即 v2.3 的"桌面之上、窗口之下"）
之后，覆盖层窗口**完全收不到鼠标消息** —— 窗口过程里的 `WM_NCHITTEST` 与
`WM_MOUSEMOVE` 计数**恒为 0**（计数器见 `LayeredOverlayWindow.HitTestSeen`），
尽管：

- `WindowFromPoint` 在任务栏的每个采样点都返回本窗口；
- 窗口确实可见（截图里看得见玻璃）；
- exStyle = `0x08080080`，含 `WS_EX_LAYERED | WS_EX_TOOLWINDOW | WS_EX_NOACTIVATE`，
  **没有** `WS_EX_TRANSPARENT`；
- 光标位置用 `SetCursorPos` 与 `mouse_event` 两种注入方式都实测过，都落点正确。

**v2.4.2 的解决办法：既然消息收不到，就主动去问。**

`PollPointerInput()` 每 tick 做三件事：

| 步骤 | 调用 | 说明 |
|---|---|---|
| 取光标 | `GetCursorPos` | 屏幕坐标 → 面板局部坐标，`HitTest` 得到命中项 |
| 取按键 | `GetAsyncKeyState(VK_LBUTTON/RBUTTON/MBUTTON)` | 直接问系统此刻的按键状态 |
| 判定 | 按下与松开**落在同一项**才算点击 | 中途滑开即取消，与真实按钮语义一致 |

悬停高亮、中键新开、右键原生菜单全部接到这一条路上（原先都挂在 `WM_MOUSEMOVE` /
`WM_LBUTTONUP` 上，一起失效）。悬停胶囊用的是同一套轮询。

**踩过的坑**：一度用 `GetAsyncKeyState` 的 `0x0001` 位（"自上次调用以来被按过"）
兜底"两次轮询之间完成的极快点击"。但该位 **MSDN 明确标注不可靠**，
实测在主路径刚处理完的那一帧仍为热 → **一次点击触发两次**
（应用被激活后立刻又被最小化）。已去掉：轮询约 30Hz，人的点击至少几十毫秒，
主路径必然采得到。

**仍然存在的副作用**：覆盖层对鼠标是透明的，注入的点击会**同时落到它背后的窗口**上
（Windows 按正常规则分发）。点图标时若背后是桌面，表现为"顺便点了一下桌面"，无副作用。
若要彻底消除，需要把覆盖层改成"可命中"并在其上自己做命中裁剪 —— 但那会挡住下层窗口，
与"窗口之下"的定位冲突，权衡后保留现状。

**一条普适经验**：**Z 序沉底的覆盖层不能指望鼠标消息。**
任何交互（悬停、点击、拖拽）都要么轮询，要么另想办法。
排查时先把 `WM_NCHITTEST` / `WM_MOUSEMOVE` 计数器打出来 ——
`WindowFromPoint` 返回你**不代表**输入会到你这里。

## 十、仍然存在的限制

| 限制 | 说明 |
|------|------|
| **系统托盘消失了** | 时钟与快捷设置入口已补，但音量/网络/电池的**图标**没有还原（那需要从 explorer 进程里抠 ToolbarWindow32 的按钮，跨版本极不稳定）。日常请用 Win+A。 |
| 固定项顺序是推测的 | 见第四节。 |
| Win7 可能列出幽灵窗口 | Win7 没有 DWM cloaked 属性。 |
| 抓屏 | 默认 `excludeFromCapture=false`：抓屏时临时隐藏自己，**截图能拍到玻璃**（见 ARCHITECTURE.md）。 |
| 与第三方任务栏工具冲突 | TranslucentTB / StartAllBack 等会抢同一批状态。 |
