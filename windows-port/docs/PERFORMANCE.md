# 性能与画质自适应

> 对应需求：「实时渲染」「渲染精致度、工作量、质量依据电脑性能动态调整」。
> 参数分档直接对齐上游的桌面参考值与移动降级档。

---

## 一、实时渲染是怎么做的

上游组件在 48 帧后冻结输出（`outColor = previous`）。这在浏览器里没问题，
因为网页内容一变化它就会整体重来。但对一条**常驻在桌面底部**的任务栏来说，
"冻住"意味着：窗口在玻璃背后移动、视频在播放、桌面切换壁纸时，
玻璃仍然显示着几秒前的旧画面 —— 看起来就是一块贴纸。

本移植把渲染循环改成**每帧检测 + 按需重画**：

```
每 tick（默认 33ms）
  │
  ├─ 抓取玻璃背后的屏幕像素（按档位规定的间隔节流）
  │
  ├─ 算场景指纹：降采样成 32×12 小块 → 每通道量化到 5 位 → FNV-1a 哈希
  │
  ├─ 指纹变了？
  │     ├─ 是 → 重建折射源、重置累积、立刻重画
  │     └─ 否 → 若还没收敛就继续累积下一帧；已收敛则玻璃层直接复用
  │
  └─ 有变化才重新合成上屏（图标层单独跟踪脏标记）
```

### 关键设计点

| 设计 | 为什么 |
|------|--------|
| **量化到 5 位** | 不量化的话，驱动或视频解码带来的 1 个色阶抖动会让指纹每帧都变，于是每帧重置累积，白白丢掉时间累积换来的干净度 |
| **指纹只读 384 个采样点** | 逐像素比较每帧要搬运上兆字节；降采样后成本可以忽略 |
| **场景变了就重置累积** | 不重置的话历史帧权重高达 47/48，新画面要 1.6 秒才能透出来，看起来像玻璃"卡住了"。重置后第一帧权重为 0，立刻响应 |
| **图标层与玻璃层分开脏标记** | 悬停高光、前台指示条变化时不必重算玻璃 |
| **静止时冻结** | 场景没变且已收敛 → 玻璃层直接复用，开销接近 0 |

### 实测证据

`--verify-realtime` 在玻璃背后放一块会切换图案的高对比窗口，
每换一次图案就**导出玻璃层本身**并比对（不是截图 —— 直接导出渲染管线的真实输出，
可以排除图标层与桌面其它区域的干扰，也更贴近"玻璃本身到底变没变"这个问题）：

| 阶段 | 与上一阶段的平均像素差 | 场景变化计数 |
|------|----------------------|-------------|
| 桌面 → 图案 0 | **123.02** | 2 |
| 图案 0 → 图案 1 | **93.94** | 3 |
| 图案 1 → 图案 2 | **30.76** | 4 |
| 图案 2 → 关闭恢复桌面 | **61.73** | 5 |

每一次背景变化都被捕捉并重画。

## 二、画质分档

### 档位表

| 档位 | 逐像素路径 | 静止累积 | 动态累积 | 超采样 | 抓屏间隔 | 说明 |
|------|-----------|---------|---------|--------|---------|------|
| `minimal` | 1 | 12 帧 | 2 | 1.00× | 100ms | 上网本 / 虚拟机 / 远程桌面 |
| `low` | **2** | **24 帧** | 4 | 1.00× | 66ms | **对应上游移动端档位** |
| `balanced` | 3 | 32 帧 | 6 | 1.00× | 50ms | 均衡 |
| `high` | **4** | **48 帧** | 8 | **1.25×** | 33ms | **上游桌面参考档** |
| `ultra` | 8 | 64 帧 | 12 | 1.50× | 33ms | 超出上游参考值 |

加粗的数字直接取自上游
`LIQUID_GLASS_REFERENCE.rendering`（`pathsPerPixel: 4` / `maxAccumulation: 48` / `maxDpr: 1.5`）
与 `DEFAULT_MOBILE_PERFORMANCE`（`pathsPerPixel: 2` / `maxAccumulation: 24` / `captureMinIntervalMs: 50`）。

### ⚠️ 一条不可违反的纪律：性能档只调"工作量"

上游在 `DEFAULT_MOBILE_PERFORMANCE` 的注释里写得很清楚：

> *"Optical/material values are deliberately absent: refraction, dispersion, tint
> and edge geometry stay identical to the desktop reference."*

本移植严格遵守：**折射率、色散强度、边缘带宽、染色、透镜曲线在所有档位下完全一致**。
低配机器上的玻璃和顶配机器上的**是同一块玻璃**，只是路径更少、累积更短、分辨率更低。
如果为了省性能去改光学参数，那台机器上的东西就不再是液态玻璃了。

### 超采样（精致度）

玻璃几何按 `超采样倍数 × 面板尺寸` 计算，渲染完再盒式缩回面板尺寸。
折射源（屏幕像素）**保持原始分辨率**，靠 `GlassScene.Scale` 把画布坐标换算回去 ——
把纹理一起放大只是白费内存，屏幕本身就只有那么细。

缩小时的区域平均天然做了抗锯齿：圆角边缘、对角高光、SDF 覆盖率在 1.25× 下算得更细，
平均回 1× 后过渡更平滑。这是 `high` 档相对上游"最大 1.5 DPR"的对应物。

## 三、自适应是怎么定档的

### 第一步：启动时用真实负载实测

```
① 抓一帧真实的折射源
② 用上游桌面参考配置（4 paths、1.0× 超采样）渲染两帧
   —— 第一帧空跑，把 JIT / 首次内存分配的开销排除掉
③ 拿第二帧的实测耗时，按成本模型外推各档位：
      成本 ∝ 逐像素路径数 × 超采样倍数的平方
④ 挑出"预估耗时 ≤ 单帧预算"里最高的那一档
```

**为什么不看 CPU 核数猜档位**：同样 8 核，插电和用电池、集显轻薄本和台式机、
后台有没有别的程序在抢，实际渲染速度能差三五倍。唯一可靠的办法就是拿真实负载去测。

实测日志长这样：

```
性能实测：基准 14.6ms（4 paths、1.0× 超采样、662×58），单帧预算 26ms
初始画质档位 → High  4 paths × 48 帧（动态 8）· 超采样 1.25× · 抓屏 33ms（预估 22.8ms/帧）
```

### 第二步：运行时闭环

仿照游戏里的动态画质，每帧回报实测耗时：

| 条件 | 动作 |
|------|------|
| 滑动平均 > 预算 × 1.15 且连续 4 帧 | 降一档 |
| 滑动平均 < 预算 × 0.50 且连续 24 帧 | 升一档 |
| 换档后 | 冷却 16 帧再评估，清空旧档位的耗时样本 |

滞回（1.15 / 0.50 的非对称阈值）+ 连击计数 + 冷却，三者合起来避免在档位边界来回横跳 ——
那比一直待在低档还难看。

**单帧预算 = 渲染节拍 × 0.8**，留两成余量给抓屏、合成与上屏，
否则渲染刚好卡满节拍时，整个循环会因抖动掉帧。

### 第三步：想稳定就锁档

```jsonc
"performance": { "qualityMode": "high" }   // 锁死，不做自适应
```

录屏、做演示时有用 —— 画质不会因为后台多了个程序就突然降下来。

## 四、成本模型

```
单帧渲染耗时  ≈ k × 逐像素路径数 × 画布像素数
```

累积帧数**不**计入：累积是跨帧摊开的，单帧成本与它无关（只是需要更多帧才收敛）。

所以 `RelativeCost = 路径数 × 超采样倍数²`：

| 档位 | relative cost |
|------|--------------|
| minimal | 1.0 |
| low | 2.0 |
| balanced | 3.0 |
| high | 6.25 |
| ultra | 18.0 |

以 `high` 为基准（实测 14.6ms @ 662×58 画布，1.0× 超采样基准线），
本机选到 `high` 意味着预估 22.8ms/帧，预算 26ms —— 恰好留有余量。
实测稳定在 **7.7~7.9ms/帧**，远好于预估（因为画布只有 662×58，
而基准测试包含了首次分配的开销），所以闭环会尝试升档到 `ultra`。

## 五、相关配置项

```jsonc
"performance": {
  "tickIntervalMs": 33,      // 渲染节拍，同时决定单帧预算
  "qualityMode": "auto",     // auto / minimal / low / balanced / high / ultra
  "mouseParallax": true      // 关闭可省下鼠标划过时的玻璃重算
}
```

`pathsPerPixel`、`idleAccumulation`、`movingAccumulation` 这三个旧字段已被
`qualityMode` 取代 —— 档位表统一管理它们，避免两处配置打架。
旧配置文件里的这三个字段会被忽略（不会报错）。

## 六、性能日志速查

| 日志 | 含义 |
|------|------|
| `性能实测：基准 X ms` | 启动基准测试的结果，1.0× 超采样、4 paths |
| `初始画质档位 → Y（预估 Z ms/帧）` | 外推得到的起始档位 |
| `画质降档 → ...（持续超出预算，实测 A ms / 预算 B ms）` | 闭环降档 |
| `画质升档 → ...（长期富余，...）` | 闭环升档 |
| `替换任务栏收尾：... 共处理 N 次场景变化` | 退出时的总结，N 就是实时重画的次数 |

如果日志里 `N` 一直是 0 而桌面明明在动，说明变化检测没工作 ——
大概率是场景指纹的量化阈值和实际画面变化幅度不匹配（比如壁纸过于细腻）。
把 `pathsPerPixel` 之外的档位参数调高、或反馈给我们。
